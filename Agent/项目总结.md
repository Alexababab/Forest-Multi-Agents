# 项目总结

---

## 项目名称

**林草综合防护与应急响应多智能体系统**

---

## 一、项目实现目标

构建一个基于大语言模型的多智能体协作系统，面向林业基层工作人员，实现以下核心目标：

1. **多模态现场信息采集**：支持护林员上传现场照片（虫害、病害、火灾）和文字描述。
2. **生物威胁自动识别**：通过视觉大模型分析图像，识别具体病虫害种类或火灾情况。
3. **法规政策智能检索（RAG）**：基于本地政策知识库，检索与当前案情相关的政府法规和技术方案。
4. **政务公文自动生成**：根据视觉分析和法规检索结果，自动撰写符合中国政府公文格式的正式报告。
5. **合规审查把关**：通过独立的审查智能体验证报告内容的生物学准确性和法规引用完整性，减少大模型幻觉。

---

## 二、技术栈

| 层级 | 技术选型 |
|------|----------|
| **语言** | Python 3.12 |
| **包管理** | uv（pyproject.toml） |
| **LLM 编排框架** | LangGraph 1.1（Command API 动态路由） |
| **主推理模型** | DeepSeek Chat（通过 langchain-deepseek） |
| **视觉模型** | Qwen-VL-Plus（阿里云 DashScope API） |
| **嵌入模型** | BAAI/bge-base-zh-v1.5（本地 GPU 推理） |
| **向量数据库** | ChromaDB（持久化存储） |
| **PDF 解析** | marker-pdf（基于 Surya OCR 的 GPU 解析） |
| **前端界面** | Streamlit（多模态聊天 UI） |
| **硬件加速** | NVIDIA RTX 4070 (CUDA) |
| **类型系统** | Pydantic v2 + TypedDict |
| **结构化输出** | LLM 直接输出 Pydantic 模型（ChatDeepSeek 原生支持） |

## 三、系统架构

系统采用 **Plan → Execute → Critic → Finalize** 四节点流水线架构，基于 LangGraph 有向图构建，通过 `Command(goto=...)` 实现动态路由：

```
START
  │
  ▼
planner_node ──（解析任务计划，分配工具）
  │
  ▼
executor_node ──（按依赖顺序调用工具执行任务，自循环直到全部完成）
  │
  ▼
critic_node ──（审查报告合规性）
  │         │
  │         ├── 不合格 → 打回 planner_node（最多 2 轮）
  │
  ▼
finalizer_node ──（格式化输出正式公文）
  │
  ▼
 END
```

### 四个智能体节点概览

1. **Planner（规划者）**：接收用户输入和反思反馈，生成结构化的任务计划（`Plan` = `Task` 列表）。每个 Task 指定所需工具（视觉分析 / 知识检索）和依赖关系。解析失败时自动重试（最多 3 次）。

2. **Executor（执行者）**：按依赖顺序调度任务，为每个任务绑定对应的 LangChain 工具（`vision_expert_tool` 或 `knowledge_expert_tool`），调用 LLM 提取参数后执行工具。包含熔断机制（最多 8 步微循环）和死锁检测（`__SYSTEM_DEADLOCK__`）。

3. **Critic（审查者 / 政务合规审查官）**：检查生成内容是否满足两条标准 — (a) 生物学准确性（是否命名了具体病虫害），(b) 政策引用完整性（是否引用了具体的官方 PDF 文件）。不合格则附带反思打回 Planner 重试；超过 2 轮则软降级输出带"红色警报"的可用报告。

4. **Finalizer（定稿者）**：将审查通过的数据整理为正式政府公文格式，生成标准化的中文报告。

### 两个工具

- `knowledge_expert_tool`：RAG 检索工具，使用 BGE 中文嵌入模型 + ChromaDB 进行语义相似度搜索（top-k=3）。
- `vision_expert_tool`：图像分析工具，将图像编码为 Base64 调用 Qwen-VL-Plus API，返回结构化视觉诊断。

### 离线数据管道（`data_pipline/`）

- `gpu_pdf_parser.py`：使用 Marker 将 PDF 转换为 Markdown
- `custom_chunker.py`：按"章""条"正则分块法律政策文档
- `ingest_data.py`：Markdown → 嵌入 → ChromaDB 知识库构建

## 四、已实现的功能

1. Streamlit 多模态前端，支持文本 + 图片上传，实时展示四阶段推理进度
2. LangGraph 四节点 Plan-Execute-Critic-Finalize 流水线，动态 Command 路由
3. LLM 结构化输出（Pydantic 模型），JSON 解析失败自动重试
4. 基于依赖关系的动态任务调度，支持上下文数据传递
5. 图级熔断机制（30 步 recursion_limit、8 步微循环、2 轮重规划）
6. 死锁检测与自动恢复（Critic 识别并指令 Planner 修复依赖）
7. 合规审查（生物学识别 + 法规引用双标准校验）
8. 超过重试上限的软降级（生成带警告的可用报告，而非直接失败）
9. GPU 加速（BGE 嵌入模型加载至 RTX 4070 CUDA 设备）
10. 基于 ChromaDB 的 RAG 知识库（松材线虫病防治技术方案示例）
11. PDF 到 Markdown 的法律文档解析管道
12. Qwen-VL-Plus 视觉 API 集成
13. Streamlit 会话状态管理（保留聊天历史与图片）

## 五、现有缺陷

### A. 代码级缺陷

1. **`test_tools.py` 过时且错误**：引用已废弃的 `ZHIPU_API_KEY`（实际已迁移至 `DASHSCOPE_API_KEY`）；`knowledge_expert_tool` 调用使用了错误的参数名 `disease_name`（实际参数为 `query`）；测试图片路径指向不存在的 `database/raw_pdfs/test.jpg`（实际图片在 `tests/` 目录）。

2. **`main.py` 为空占位文件**：仅打印 "Hello from agent!"，实际入口在 `app.py`。

3. **`README.md` 为空**：项目无任何使用说明或架构文档。

4. **嵌入模型加载重复**：`tools.py` 和 `ingest_data.py` 各自独立实现 BGE 模型加载逻辑，存在代码重复。

5. **硬编码 CUDA 设备**：`tools.py` 中 `model_kwargs={'device': 'cuda'}` 无 CPU 回退，非 NVIDIA 机器直接崩溃。

6. **状态解引用缺乏空值检查**：`AgentState` 的 `plan` 字段类型为 `Optional[Plan]`，但 Executor 和 Critic 代码直接访问 `state["plan"].steps`，未做 None 检查。

7. **Qwen API 图像 MIME 类型支持不完整**：仅处理 5 种扩展名（`.jpg`、`.jpeg`、`.png`、`.webp`、`.bmp`），其他格式静默回退为 `image/jpeg`，可能导致 API 调用失败。

### B. 架构级缺陷

8. **架构简单**：四个智能体本质上只是带有不同提示词的 DeepSeek Chat 调用，无微调、无专用模型、无记忆持久化。

9. **视觉识别可靠性差**：完全依赖商用视觉 API（Qwen-VL-Plus），无法微调或针对性优化，识别准确率不可控。

10. **问题定位模糊**：项目名称宏大但实际仅覆盖松材线虫病一种场景（知识库仅 `test.pdf` 一份文档），火灾和一般病虫害虽有测试图片但无对应知识库支撑。

11. **无测试基础设施**：无单元测试、无集成测试、无评估指标。`test_tools.py` 已失效。

12. **无 API 成本控制**：仅靠 30 步 recursion_limit 约束，无 token 计数、预算上限、重试退避。

13. **无输出持久化**：报告仅在 Streamlit UI 渲染，无数据库存储、无 PDF 导出、刷新页面丢失全部内容。

14. **无用户认证与审计**：任何能访问端口的人均可提交报告，无登录、无角色、无操作日志。

15. **知识库构建门槛高**：需先 GPU 解析 PDF → 分块 → 嵌入 → 写入 ChromaDB，依赖大量模型下载，无可直接使用的预构建索引。
